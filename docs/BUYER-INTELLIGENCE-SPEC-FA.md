# طراحی فنی هوش خریدار (Buyer Intelligence) — نسخه ۱

> این سند مشخصات اجرایی مرحله بعد است؛ به‌تنهایی به معنی وجود API یا قابلیت فعال در Production نیست.

## 1. هدف و مرز مسئولیت

Buyer Intelligence درخواست آزاد خریدار را به مشخصات قابل جست‌وجو تبدیل می‌کند، کاتالوگ موجود را با فیلترهای قابل توضیح بررسی می‌کند و گزینه‌ها را همراه با دلیل، محدودیت و منبع نمایش می‌دهد.

این لایه جایگزین بازارگاه موجود نیست. endpoint کاتالوگ فعلی `GET /api/stores` منبع جست‌وجوی محصول است. ثبت سفارش همچنان از مسیر `POST /api/store/orders` و فقط پس از اقدام صریح کاربر انجام می‌شود.

در نسخه نخست، هوش مصنوعی نباید قیمت، موجودی، گواهی فروشنده، زمان تحویل یا ویژگی فنی را حدس بزند. داده‌های محصول و فروشگاه از پایگاه داده خوانده می‌شوند؛ نتیجه ناموجود باید «اطلاعات کافی نیست» باشد.

## 2. جریان کار

1. کاربر نیاز را به زبان طبیعی وارد می‌کند.
2. سیستم زبان و متن را تشخیص می‌دهد؛ در صورت ابهام سؤال تکمیلی می‌پرسد.
3. مشخصات صریح را استخراج می‌کند: عبارت جست‌وجو، دسته، شهر/منطقه انتخابی، بودجه و ارز، تعداد، روش دریافت و ویژگی‌های فنی.
4. هر فیلد با منشأ آن ذخیره می‌شود: user_provided، parsed_from_text یا inferred. فیلد inferred به‌تنهایی مجوز فیلتر سخت یا ادعای قطعی نیست.
5. فقط فیلدهای تأییدشده کاربر به فیلترهای کاتالوگ تبدیل می‌شوند.
6. نتایج موجود از `GET /api/stores` دریافت و با معیارهای آشکار مرتب می‌شوند.
7. سیستم دلیل تطبیق، داده‌های ناموجود و تاریخ بررسی را نمایش می‌دهد.
8. کاربر می‌تواند جزئیات فروشنده را ببیند، گزینه را ذخیره کند یا خودش درخواست سفارش ثبت کند.

## 3. قرارداد API پیشنهادی

### POST /api/v1/buyer/needs/analyze

ورودی:

```json
{
  "text": "برای کارگاه نجاری دستگاه CNC می‌خواهم، بودجه‌ام ...",
  "locale": "fa",
  "countryCode": "IR",
  "confirmedFields": {}
}
```

خروجی پیشنهادی:

```json
{
  "needId": "uuid",
  "status": "needs_clarification",
  "parsed": {
    "query": "دستگاه CNC نجاری",
    "category": null,
    "city": null,
    "budget": null,
    "quantity": null,
    "fulfillmentMode": null,
    "technicalRequirements": []
  },
  "missingFields": ["budget_currency"],
  "questions": [],
  "notice": "فیلدهای استخراج‌شده پیش از جست‌وجوی محدودکننده باید تأیید شوند."
}
```

### POST /api/v1/buyer/needs/{id}/confirm

کاربر فیلدهای درست را تأیید یا اصلاح می‌کند. تأیید باید به شناسه کاربر متصل باشد؛ هیچ تأیید خودکاری از طرف عامل هوش مصنوعی پذیرفته نمی‌شود.

### GET /api/v1/buyer/needs/{id}/matches

خروجی هر نتیجه:
- productId و storeId
- قیمت و ارز دقیقاً مطابق رکورد محصول
- موجودی ثبت‌شده، با زمان آخرین به‌روزرسانی
- شهر، روش دریافت و اطلاعات تماس عمومی
- دلایل تطبیق
- مواردی که داده آن‌ها موجود نیست
- لینک/مسیر مشاهده محصول
- سطح اعتماد فروشگاه و منبع، فقط اگر واقعاً ثبت و تأیید شده باشد

### POST /api/v1/buyer/needs/{id}/feedback

ثبت اینکه نتیجه مناسب، نامناسب یا ناقص بوده است؛ برای بهبود تطبیق، نه دستکاری رتبه فروشنده.

## 4. مدل داده پیشنهادی

### buyer_needs
- id, user_id, raw_text, locale, country_code
- status, created_at, updated_at

### buyer_need_fields
- id, need_id, field_key, field_value_json
- source: user_provided | parsed_from_text | inferred
- confidence, user_confirmed, updated_at

### buyer_need_matches
- id, need_id, product_id, store_id
- match_reasons_json, missing_data_json
- score_breakdown_json, catalog_snapshot_at, created_at

### buyer_need_feedback
- id, need_id, product_id, user_id
- feedback_type, note, created_at

هیچ داده مکانی دقیق کاربر بدون رضایت صریح ذخیره نشود. کشور، شهر و ارز باید از انتخاب کاربر یا تنظیمات صریح او گرفته شوند، نه حدس IP.

## 5. موتور تطبیق و رتبه‌بندی قابل توضیح

نسخه اول از فیلترهای قطعی و امتیازدهی ساده استفاده می‌کند:

- تطابق عبارت و دسته: 0 تا 30
- تطابق ویژگی‌های فنی تأییدشده: 0 تا 25
- تطابق بودجه و ارز قابل مقایسه: 0 تا 20
- روش دریافت انتخابی: 0 تا 10
- تازگی داده محصول: 0 تا 10
- کامل‌بودن اطلاعات فروشنده: 0 تا 5

قواعد:
- فیلد ناموجود امتیاز مثبت نمی‌گیرد.
- قیمت دو ارز متفاوت بدون نرخ معتبر و زمان‌دار مقایسه نمی‌شود.
- موجودی صفر یا محصول منتشرنشده از نتایج خرید حذف می‌شود.
- تبلیغ پولی هیچ امتیاز تطبیقی ایجاد نمی‌کند.
- امتیاز کلی همراه با breakdown و دلایل نمایش داده می‌شود.
- رتبه‌بندی فقط برای کمک به انتخاب است و تضمین کیفیت یا مناسب‌بودن فنی نیست.

## 6. کنترل‌های امنیت و حریم خصوصی

- نیاز خصوصی فقط برای مالک و نقش‌های مجاز قابل مشاهده است.
- endpointهای ایجاد، تأیید و بازخورد نیازمند نشست معتبر، Origin check، rate limit و اعتبارسنجی بدنه هستند.
- متن کاربر و توضیحات فروشنده ورودی غیرقابل‌اعتمادند؛ دستورهای داخل متن نباید به عامل اجازه تغییر policy یا اجرای ابزار بدهند.
- اطلاعات حساس، شماره تماس خصوصی، آدرس منزل و اسناد هویتی وارد prompt یا خروجی عمومی نشوند.
- درخواست حذف داده و retention policy باید پیش از عرضه عمومی تعریف شود.
- عامل فقط مجاز به تحلیل و پیشنهاد است؛ ثبت سفارش، تماس با فروشنده یا پرداخت نیازمند اقدام/تأیید کاربر است.

## 7. معیارهای پذیرش

1. متن فارسی و انگلیسی بدون از دست رفتن ورودی اصلی پذیرفته شود.
2. بودجه بدون ارز یا عدد مبهم به‌عنوان بودجه قطعی تفسیر نشود.
3. شهر یا مختصات از روی IP حدس زده نشود.
4. محصول منتشرنشده و فروشگاه غیرفعال در نتیجه نیاید.
5. هر دلیل تطبیق به فیلد واقعی محصول یا فروشگاه متصل باشد.
6. امتیاز با داده ساختگی یا ویژگی حدس‌زده‌شده افزایش نیابد.
7. هیچ سفارش یا پیام به فروشنده بدون اقدام کاربر ایجاد نشود.
8. دسترسی کاربر به نیازهای سایر کاربران با آزمون منفی رد شود.
9. تست‌ها شامل prompt injection در متن نیاز و توضیحات کالا باشند.
10. خطای مدل هوش مصنوعی به نتیجه موفق کاذب تبدیل نشود؛ fallback به جست‌وجوی عادی کاتالوگ ارائه شود.

## 8. ترتیب پیاده‌سازی

1. ساخت migration جداول نیاز خریدار و بازخورد
2. افزودن API ثبت و بازیابی نیاز با کنترل مالکیت
3. افزودن parser ساختاریافته با fallback ساده و بدون وابستگی اجباری به مدل خارجی
4. افزودن تأیید صریح فیلدهای استخراج‌شده
5. اتصال امن به کاتالوگ `GET /api/stores`
6. افزودن امتیازدهی قابل توضیح و ثبت feedback
7. افزودن رابط فارسی/انگلیسی
8. تست D1، تست دسترسی، rate limit، prompt injection و end-to-end در staging

## 9. وابستگی‌ها و محدودیت‌ها

- وابسته به محصولات منتشرشده، فروشگاه‌های فعال و داده درست قیمت/ارز است.
- کاتالوگ فعلی `GET /api/stores` در query پارامترهای `q`, `city`, `region`, `mode`, `lat`, `lon`, `limit`, `offset` را می‌پذیرد.
- این endpoint در حال حاضر حداکثر 501 رکورد تازه را واکشی و سپس صفحه‌بندی می‌کند؛ برای کاتالوگ بزرگ، pagination دیتابیسی و indexهای متناسب باید پیش از مقیاس جهانی طراحی شوند.
- endpoint `GET /api/store/products` نیز مسیر جداگانه‌ای با قابلیت فیلتر category دارد؛ دو قرارداد نباید بدون تصمیم معماری با یکدیگر ادغام یا اشتباه گرفته شوند.

## 10. خارج از نسخه اول

- مذاکره خودکار با فروشنده
- خرید خودکار یا پرداخت
- تبدیل ارز بدون نرخ معتبر و زمان‌دار
- تضمین کیفیت یا اصالت محصول
- رتبه‌بندی پولی پنهان
- تشخیص نیازهای حساس یا استنتاج ویژگی‌های شخصی کاربر
