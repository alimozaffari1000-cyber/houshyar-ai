# چک‌لیست انتشار امن هوش‌یار

این سند چک‌لیست عملیاتی انتشار است؛ وجود کد در GitHub به معنی آماده‌بودن سرویس برای کاربران واقعی نیست.

## ۱. ترتیب ادغام کد

- [ ] وابستگی‌های تغییرات حساب کاربری و امنیت را به‌ترتیب وابستگی PRها بازبینی و ادغام کنید: پایه D1، محدودیت نرخ چت، احراز هویت، سهمیه روزانه، سخت‌سازی احراز هویت، سپس تأیید ایمیل و بازیابی رمز.
- [ ] پس از هر ادغام، شاخه بعدی را با شاخه مقصد به‌روز کنید و CI را دوباره اجرا کنید.
- [ ] هیچ PR را صرفاً به‌دلیل بازبودن یا داشتن تست، بدون بررسی تغییرات و نتیجه CI ادغام نکنید.

## ۲. آماده‌سازی Cloudflare

- [ ] یک پایگاه D1 اختصاصی برای محیط production بسازید.
- [ ] binding پایگاه داده را با نام دقیق `DB` به Pages/Worker متصل کنید.
- [ ] migrationهای `0001`، `0002` و `0003` را به‌ترتیب روی پایگاه production اعمال کنید.
- [ ] قبل از migration، از داده‌های موجود نسخه پشتیبان بگیرید و اجرای migration را در محیط آزمایشی بررسی کنید.
- [ ] دامنه HTTPS نهایی را در `APP_BASE_URL` قرار دهید.
- [ ] یک سرویس ارسال ایمیل با endpoint مبتنی بر HTTPS و قرارداد JSON مستندشده آماده کنید.
- [ ] مقادیر `EMAIL_API_URL`، `EMAIL_API_KEY` و `EMAIL_FROM` را فقط در بخش Secrets/Environment Variables سمت سرور تنظیم کنید؛ هیچ‌کدام نباید در کد یا متغیرهای `VITE_*` قرار بگیرند.

نمونه فرمان اعمال migration پس از تنظیم binding و نام پایگاه:

```bash
npx wrangler d1 migrations apply houshyar-ai-db --remote
```

نام پایگاه باید با نام واقعی D1 ساخته‌شده در Cloudflare تطبیق داشته باشد.

## ۳. تنظیم تدریجی قابلیت‌ها

- [ ] ابتدا نسخه production با `AUTH_ENABLED` خاموش منتشر شود.
- [ ] مسیرهای چت، خطاهای API، timeout، محدودیت اندازه درخواست و گزارش‌های امنیتی بررسی شوند.
- [ ] پس از اتصال D1 و ایمیل، ثبت‌نام، تأیید ایمیل، ورود، خروج، ارسال مجدد تأیید و بازیابی رمز با حساب‌های آزمایشی بررسی شوند.
- [ ] انقضای توکن‌ها، یک‌بارمصرف‌بودن آن‌ها، ابطال نشست‌ها پس از تغییر رمز و پاسخ یکسان برای ایمیل‌های موجود/ناموجود آزمایش شود.
- [ ] محدودیت نرخ login/register و مسیرهای ایمیل، محدودیت چت و سهمیه روزانه با چند حساب آزمایشی بررسی شوند.
- [ ] فقط پس از موفقیت همه بررسی‌ها، `AUTH_ENABLED=true` و سپس در صورت نیاز `CHAT_QUOTA_ENABLED=true` فعال شوند.

## ۴. نگهداری و کنترل هزینه

- [ ] پاک‌سازی زمان‌بندی‌شده توکن‌های مصرف‌شده/منقضی، نشست‌های منقضی/باطل و ردیف‌های rate-limit پیاده‌سازی و در محیط آزمایشی بررسی شود.
- [ ] سقف هزینه و مصرف provider مدل، محدودیت درخواست، timeout و هشدار خطا تنظیم شوند.
- [ ] لاگ‌ها نباید رمز عبور، توکن خام، کلید API، متن خصوصی کاربر یا IP خام را ثبت کنند.
- [ ] دسترسی GitHub Actions و Cloudflare بر اساس حداقل سطح دسترسی باقی بماند.
- [ ] قبل از بازکردن عمومی سرویس، سیاست حریم خصوصی و شرایط استفاده توسط فرد واجد صلاحیت بررسی شوند.

## ۵. معیار پذیرش انتشار

انتشار عمومی فقط وقتی مجاز است که:
1. تمام PRهای وابسته ادغام شده باشند و CI روی شاخه نهایی سبز باشد.
2. build و تست‌های واحد، امنیتی و کیفیت موفق باشند.
3. D1، migrationها، ایمیل HTTPS و دامنه production آزمایش شده باشند.
4. تست end-to-end ثبت‌نام تا بازیابی رمز موفق باشد.
5. محدودیت نرخ، سهمیه و کنترل هزینه در محیط production فعال و قابل مشاهده باشند.
6. برنامه پشتیبان‌گیری، بازگشت نسخه و پاسخ به رخداد امنیتی مشخص باشد.

**هشدار:** تست‌های خودکار جایگزین تست نفوذ، بازبینی حقوقی یا ارزیابی امنیت محیط واقعی نیستند. تا تکمیل موارد بالا، احراز هویت و سهمیه‌بندی را در production فعال نکنید.
