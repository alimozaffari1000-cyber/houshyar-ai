# چرخه عمر داده و حریم خصوصی هوش‌یار

وضعیت: مشخصات محصول و معیار پذیرش؛ این سند به‌تنهایی قابلیت اجرایی ایجاد نمی‌کند.

## هدف

هوش‌یار باید برای ارائه خدمات مفید، حداقل داده لازم را دریافت کند و اختیار واقعی کاربر را درباره نگهداری، استفاده، خروجی‌گرفتن و حذف داده فراهم کند. «حافظه هوشمند» نباید به معنی ذخیره نامحدود گفتگوها یا استفاده پنهانی از اطلاعات باشد.

## اصول غیرقابل‌مذاکره

1. **حداقل‌سازی داده:** فقط داده‌ای ذخیره شود که برای یک قابلیت مشخص لازم است؛ هدف و مدت نگهداری آن مشخص باشد.
2. **رضایت جداگانه و قابل‌پس‌گرفتن:** حافظه شخصی، تحلیل استفاده برای بهبود محصول، پیام‌های بازاریابی و اتصال سرویس‌های ثالث رضایت‌های جداگانه‌اند. فعال‌بودن یکی، مجوز دیگری نیست.
3. **خاموشی پیش‌فرض برای حافظه پایدار:** تا زمانی که کاربر حافظه را روشن نکرده، اطلاعات گفتگو نباید به پروفایل پایدار منتقل شود.
4. **جداسازی کاربران:** هر پرس‌وجو و عملیات خواندن/نوشتن/حذف باید در سمت سرور به هویت احرازشده و مالکیت رکورد محدود باشد؛ شناسه ارسالی مرورگر به‌تنهایی مدرک مالکیت نیست.
5. **عدم ذخیره اسرار:** رمز عبور، کلید API، توکن نشست، اطلاعات پرداخت و داده‌های بسیار حساس نباید وارد حافظه شخصی یا گزارش‌های عملیاتی شوند.
6. **شفافیت:** کاربر باید بتواند ببیند چه دسته‌ای از اطلاعات ذخیره شده، چرا ذخیره شده و از کدام قابلیت استفاده می‌شود.
7. **حذف واقعی و قابل‌پیگیری:** حذف باید رکوردهای اصلی و نسخه‌های مشتق‌شده/ایندکس‌شده را پوشش دهد و وضعیت حذف ناموفق یا ناقص پنهان نشود.
8. **بدون آموزش مدل از داده کاربر به‌صورت پیش‌فرض:** استفاده برای آموزش یا ارزیابی مدل نیازمند انتخاب صریح و مستقل است؛ خاموش‌کردن این گزینه نباید قابلیت اصلی محصول را مختل کند.

## طبقه‌بندی داده

| دسته | نمونه | سیاست پیشنهادی |
|---|---|---|
| داده حساب | شناسه داخلی، ایمیل تأییدشده، تنظیمات زبان | فقط برای حساب و امنیت؛ دسترسی محدود |
| تنظیمات شخصی | زبان، منطقه زمانی، ترجیحات رابط | اختیاری؛ قابل مشاهده و حذف |
| حافظه انتخابی | ترجیحات یا پروژه‌هایی که کاربر صریحاً ذخیره می‌کند | فقط با رضایت روشن؛ قابل ویرایش و حذف |
| تاریخچه گفتگو | پیام‌های کاربر و پاسخ‌ها | سیاست نگهداری مستقل و قابل تنظیم؛ عدم انتقال خودکار به حافظه |
| داده عملیاتی | زمان پاسخ، کد وضعیت، ارائه‌دهنده مدل | حداقلی و بدون متن گفتگو، prompt، کلید یا شناسه مستقیم |
| داده مالی/سفارش | سفارش، اعتبار، رویداد پرداخت | جداسازی از حافظه؛ نگهداری طبق الزام قانونی و حسابداری |
| داده حساس | سلامت، هویت، موقعیت دقیق، اطلاعات مالی حساس | عدم ورود به حافظه عمومی؛ فقط در قابلیت تخصصی با کنترل و رضایت مناسب |

## کنترل‌هایی که باید در محصول ارائه شوند

### مرکز حریم خصوصی
- وضعیت حافظه شخصی: خاموش / روشن.
- فهرست حافظه‌های ذخیره‌شده با زمان ایجاد و دلیل ذخیره.
- ویرایش و حذف یک مورد و پاک‌سازی همه حافظه‌های انتخابی.
- خروجی قابل‌خواندن از داده‌های حساب و حافظه.
- تنظیم مستقل تاریخچه گفتگو و انتخاب بازه نگهداری، در صورت پشتیبانی فنی.
- تنظیم مستقل استفاده پژوهشی/آموزشی از داده؛ پیش‌فرض خاموش.
- صفحه توضیح درخواست حذف حساب و پیامدهای آن، از جمله داده‌هایی که به دلیل الزام قانونی قابل حذف فوری نیستند.

### مسیر حذف
1. درخواست حذف با احراز هویت مجدد و محافظت در برابر CSRF ثبت شود.
2. عملیات دارای شناسه پیگیری و وضعیت‌های `requested`، `processing`، `completed` یا `failed` باشد.
3. داده‌های اصلی، حافظه‌ها، ایندکس‌ها، فایل‌های خصوصی و کش‌های قابل‌کنترل در دامنه حذف قرار گیرند.
4. نسخه‌های پشتیبان طبق چرخه انقضای مستند پاک شوند؛ تا آن زمان داده حذف‌شده نباید به محصول بازگردد.
5. سوابقی که قانوناً باید نگهداری شوند از محتوای محصول جدا و فقط با دسترسی محدود نگهداری شوند.
6. پاسخ نهایی به کاربر دقیق باشد؛ حذف ناقص هرگز «کامل شد» گزارش نشود.

## امنیت و معماری

- کنترل دسترسی در هر endpoint سمت سرور انجام شود؛ الگوی پیش‌فرض deny باشد.
- تمام queryهای D1 برای داده کاربر باید مالکیت را در شرط SQL اعمال کنند.
- فایل‌های کاربر در R2 خصوصی بمانند؛ URL عمومی دائمی برای داده خصوصی ساخته نشود.
- عملیات حذف چندمنبعی باید idempotent باشد تا retry باعث خطا یا باقی‌ماندن داده نشود.
- گزارش‌های عملیاتی فقط شناسه درخواست تصادفی، route مجاز، provider، status و زمان را ثبت کنند؛ نه متن پیام، prompt، ایمیل، IP خام یا credential.
- کلیدهای رمزنگاری و secrets هرگز در مرورگر، پاسخ API یا log قرار نگیرند.
- دسترسی کارکنان/مدیران به داده کاربر باید محدود، ثبت‌شده و مبتنی بر نیاز عملیاتی باشد.

## APIهای پیشنهادی برای مرحله پیاده‌سازی

این مسیرها صرفاً قرارداد پیشنهادی‌اند و تا زمان پیاده‌سازی و تست نباید در رابط کاربری به‌عنوان قابلیت فعال نمایش داده شوند:

- `GET /api/privacy/summary` — تنظیمات و دسته‌های داده کاربر.
- `GET /api/memory` — فهرست حافظه‌های انتخابی همان کاربر.
- `PATCH /api/memory/:id` — ویرایش مورد متعلق به کاربر.
- `DELETE /api/memory/:id` — حذف idempotent یک مورد.
- `DELETE /api/memory` — پاک‌سازی حافظه‌های انتخابی.
- `POST /api/privacy/export` — ایجاد درخواست خروجی داده.
- `POST /api/privacy/deletion` — ثبت درخواست حذف حساب و داده.

هر endpoint باید احراز هویت، کنترل مالکیت، اعتبارسنجی ورودی، محدودیت نرخ، پاسخ خطای بدون افشای جزئیات و تست مستقل داشته باشد.

## معیارهای پذیرش پیش از انتشار

- کاربر A با تغییر شناسه رکورد نتواند حافظه یا فایل کاربر B را بخواند، تغییر دهد یا حذف کند.
- حافظه پایدار با خاموش بودن رضایت، حتی در مسیرهای خودکار، ایجاد نشود.
- پس‌گرفتن رضایت مانع ذخیره‌های جدید شود و وضعیت داده‌های قبلی را روشن نمایش دهد.
- حذف یک مورد و حذف همه موارد در برابر retry ایمن و idempotent باشد.
- داده حساس و اسرار در API response، log، analytics و export ناخواسته ظاهر نشوند.
- خطای D1/R2 یا هر منبع وابسته باعث گزارش موفقیت کاذب نشود.
- تست‌های CSRF، IDOR، tenant isolation، rate limit، retention و حذف ناقص اجرا شوند.
- تست end-to-end در محیط staging با داده ساختگی انجام شود؛ هیچ migration روی Production بدون بررسی تاریخچه واقعی D1 و تأیید انسانی اجرا نشود.

## ترتیب اجرا

1. ممیزی مسیرهای فعلی حساب، گفتگو، D1، R2 و logها.
2. طراحی migrationها و مدل رضایت با بررسی سازگاری با schema واقعی.
3. پیاده‌سازی APIهای خواندن/ویرایش/حذف حافظه با تست جداسازی کاربران.
4. ساخت مرکز حریم خصوصی و خروجی داده.
5. پیاده‌سازی صف حذف چندمنبعی و گزارش وضعیت دقیق.
6. آزمون امنیتی و end-to-end در staging.
7. انتشار مرحله‌ای پس از بررسی انسانی؛ بازگشت‌پذیری migration و پایش خطا الزامی است.

## خارج از محدوده این مرحله

این سند هیچ ادعایی درباره فعال‌بودن حافظه پایدار، حذف حساب، export، رمزنگاری اختصاصی، گواهی انطباق قانونی یا اجرای migration ندارد. این موارد فقط پس از پیاده‌سازی، تست و بررسی محیط واقعی قابل اعلام‌اند.
