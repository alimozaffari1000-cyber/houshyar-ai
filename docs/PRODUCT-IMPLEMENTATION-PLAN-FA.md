# نقشه اجرایی نسخه اول هوش‌یار (MVP)

> وضعیت این سند: برنامه‌ریزی فنی؛ به‌معنای پیاده‌سازی یا فعال‌بودن قابلیت‌ها نیست.

## 1. تصمیم معماری

نسخه اول با معماری Modular Monolith روی Cloudflare Pages و Pages Functions ادامه می‌یابد. رابط فعلی Vite در `src/` و APIها در `functions/api/` باقی می‌مانند. داده‌های پایدار در Cloudflare D1 ذخیره می‌شوند. ماژول‌ها باید مرزهای روشن، قرارداد API و مالکیت داده مشخص داشته باشند تا در آینده قابل جداسازی باشند.

از ایجاد microserviceهای متعدد، کیف پول داخلی و پرداخت واقعی در فاز نخست خودداری می‌شود.

## 2. یافته‌های تأییدشده از شاخه main

- رابط اصلی در `src/main.js` ساخته می‌شود.
- ماژول بازارگاه فرانت‌اند در `src/marketplace.js` وجود دارد.
- بازارگاه فعلی قابلیت مرور محصولات، درخواست ایجاد فروشگاه، ثبت محصول، مدیریت وضعیت محصول و درخواست سفارش را در رابط دارد.
- متن رابط بازارگاه در نسخه بررسی‌شده برای فارسی و انگلیسی تعریف شده است؛ این موضوع با پشتیبانی کامل چندزبانه محصول یکسان نیست.
- API گفت‌وگو در `functions/api/chat.js` قرار دارد.
- ارائه‌دهندگان Groq، Anthropic و Gemini در `functions/api/_lib/model-providers.js` پیاده‌سازی شده‌اند.
- پیکربندی Wrangler از `pages_build_output_dir = "./dist"` استفاده می‌کند؛ پروژه باید به‌صورت Cloudflare Pages منتشر شود، نه Workers Builds.
- README شاخه main می‌گوید migrationهای D1 از 0001 تا 0006 هستند و پیش از فعال‌سازی تولیدی باید binding، ترتیب migrationها، سرویس ایمیل و آزمون end-to-end بررسی شوند.
- وجود کد یا migration به‌تنهایی اثبات نمی‌کند قابلیت در Production فعال و سالم است.

## 3. محدوده MVP

### 3.1 هویت و حساب
- ثبت‌نام، ورود، خروج و بازیابی امن حساب
- نشست امن و محافظت از مسیرهای خصوصی
- نقش‌های پایه: user، seller، moderator و admin
- کنترل دسترسی سمت سرور؛ مخفی‌کردن دکمه در رابط، کنترل امنیتی محسوب نمی‌شود.

### 3.2 بازارگاه داخلی
- پروفایل فروشگاه و وضعیت بررسی آن
- ثبت و ویرایش محصول
- جست‌وجو و فیلتر بر اساس عبارت، دسته، منطقه و روش تحویل
- درخواست سفارش بدون پرداخت آنلاین در فاز نخست
- پنل فروشنده برای محصولات و سفارش‌ها
- گزارش تخلف و مسیر تعلیق فروشگاه یا محصول

### 3.3 نیازها و تطبیق
- ثبت نیاز خریدار یا متقاضی خدمت
- تبدیل نیاز به دسته، ویژگی‌ها، بودجه اختیاری و منطقه انتخابی
- تطبیق با کالا، خدمات و فروشندگان موجود
- نمایش دلیل تطبیق و سطح اعتبار منبع
- امکان رد، ذخیره یا گزارش نتیجه نامناسب

### 3.4 فرصت‌ها
- ثبت فرصت شغلی و پروژه‌ای
- پروفایل مهارت کاربر با شواهد اختیاری
- درخواست همکاری و پیگیری وضعیت
- بررسی اعتبار کارفرما و منبع آگهی
- فرصت‌های سرمایه‌گذاری در این فاز صرفاً پژوهشی و اطلاع‌رسانی هستند؛ بدون دریافت پول یا وعده سود.

### 3.5 مدیریت و اعتماد
- صف بررسی فروشگاه‌ها و گزارش‌ها
- ثبت رویدادهای مدیریتی و امنیتی
- نشان‌دادن جداگانه وضعیت تأیید هویت، تأیید کسب‌وکار و سابقه عملکرد
- جداسازی تبلیغ پولی از رتبه و اعتبار واقعی

## 4. ماژول‌های پیشنهادی

| ماژول | مسئولیت |
|---|---|
| identity | حساب، نشست، نقش و دسترسی |
| marketplace | فروشگاه، محصول و سفارش |
| needs | ثبت نیاز و چرخه رسیدگی |
| matching | تطبیق نیاز با عرضه |
| opportunities | شغل، پروژه و فرصت کسب‌وکار |
| trust | اعتبارسنجی و گزارش تخلف |
| country-config | زبان، ارز، منطقه و قابلیت‌های مجاز کشور |
| notifications | اعلان درون‌برنامه‌ای و ایمیل |
| audit | رویدادهای امنیتی و مدیریتی |

## 5. اصول داده و امنیت

- تمام مالکیت‌ها و مجوزها در سرور کنترل شوند.
- هر رکورد خصوصی باید مالک یا دامنه سازمانی مشخص داشته باشد.
- ورودی‌ها در سرور اعتبارسنجی و خروجی‌ها هنگام نمایش escape شوند.
- عملیات حساس باید CSRF، rate limit و کنترل مجوز مناسب داشته باشند.
- کلیدها فقط در Cloudflare Secrets باشند؛ هیچ Secret در Git یا متغیرهای VITE قرار نگیرد.
- داده مکانی فقط با انتخاب و رضایت کاربر استفاده شود؛ کشور پیش‌فرض از روی IP یا حدس تعیین نشود.
- اطلاعات مالی و هویتی حداقلی جمع‌آوری و دوره نگهداری آن‌ها تعریف شود.
- عملیات مدیر و عامل هوش مصنوعی باید audit شوند.
- هیچ عامل هوش مصنوعی مجاز به تغییر مجوز خود، پاک‌کردن audit log یا انتشار Production بدون تأیید انسانی نیست.

## 6. ترتیب اجرا

### فاز A — ممیزی و تثبیت
1. بررسی تمام مسیرهای API و migrationهای موجود
2. بررسی اتصال واقعی D1 و تطبیق migration history
3. اجرای `npm run qa`، `npm run agent:check`، `npm run security:scan` و `npm run build`
4. رفع خطاهای موجود بدون تغییر رفتار سالم
5. ثبت وضعیت هر قابلیت: کدنویسی‌شده، تست‌شده، پیکربندی‌شده، منتشرشده

### فاز B — تکمیل بازارگاه
1. ممیزی APIهای فروشگاه، محصول و سفارش
2. آزمون مالکیت داده و مجوزهای فروشنده
3. تکمیل گزارش تخلف و کنترل مدیر
4. آزمون جست‌وجو، صفحه‌بندی و ورودی‌های نامعتبر
5. آزمون end-to-end در محیط آزمایشی

### فاز C — نیاز و تطبیق
1. مدل داده نیازها و دسته‌بندی‌ها
2. API ثبت و پیگیری نیاز
3. موتور تطبیق قابل توضیح
4. اتصال به محصولات و فروشگاه‌های موجود
5. آزمون کیفیت تطبیق و جلوگیری از نمایش نتایج ساختگی

### فاز D — فرصت‌ها
1. آگهی شغلی و پروژه
2. پروفایل مهارت و درخواست همکاری
3. ارزیابی منبع و کارفرما
4. داشبورد پیگیری درخواست‌ها

### فاز E — آماده‌سازی انتشار
1. پیکربندی Pages، D1، Secrets و ایمیل
2. اجرای migrationها ابتدا در staging
3. آزمون ثبت‌نام، ورود، بازارگاه و APIها در staging
4. پشتیبان‌گیری و برنامه rollback
5. بررسی حقوقی، حریم خصوصی و شرایط استفاده پیش از عرضه عمومی

## 7. معیارهای پذیرش

- کاربر بدون ورود به پنل خصوصی فروشنده دسترسی ندارد.
- فروشنده فقط داده‌های متعلق به خود را مدیریت می‌کند.
- سفارش بدون پرداخت، فقط یک درخواست قابل پیگیری است.
- فروشگاه تأییدنشده به‌عنوان تأییدشده نمایش داده نمی‌شود.
- هر پیشنهاد تطبیق، دلیل و سطح اطمینان قابل مشاهده دارد.
- خطای D1 یا سرویس بیرونی باعث افشای اطلاعات یا موفقیت کاذب نمی‌شود.
- آزمون‌های واحد، امنیتی و end-to-end برای مسیرهای حیاتی سبز هستند.
- هیچ Secret در خروجی build یا مخزن وجود ندارد.

## 8. موارد خارج از MVP

- تسویه و کیف پول چندارزی
- پرداخت رمزارزی
- تجارت فرامرزی خودکار و اسناد گمرکی
- امتیازدهی اعتباری مالی
- تصمیم‌گیری سرمایه‌گذاری خودکار
- عامل خودمختار با مجوز انتشار Production
- ادعای پشتیبانی کامل از همه زبان‌ها و همه کشورها

این موارد فقط پس از تکمیل الزامات حقوقی، امنیتی، عملیاتی و تأمین‌کنندگان مجاز وارد برنامه می‌شوند.

## 9. اصل انتشار

هیچ تغییر این سند به‌تنهایی نباید روی شاخه main یا Production اعمال شود. تغییرات اجرایی ابتدا در شاخه جداگانه، سپس با تست و بازبینی و Pull Request ارائه می‌شوند. ادغام و انتشار نهایی باید پس از مشاهده نتیجه تست و تأیید انسانی انجام شود.
