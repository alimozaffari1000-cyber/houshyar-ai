## 2. کنترل‌هایی که در کد مشاهده شد

1. مسیرهای نوشتن فروشگاه، محصول و سفارش احراز هویت نشست را بررسی می‌کنند.
2. مسیرهای نوشتن Origin را با مبدأ درخواست تطبیق می‌دهند.
3. برای عملیات مهم محدودیت نرخ درخواست وجود دارد.
4. فروشنده فقط برای فروشگاه متعلق به حساب خود محصول ثبت می‌کند.
5. محصول جدید ابتدا با وضعیت draft ثبت می‌شود و انتشار به فروشگاه فعال محدود است.
6. کاتالوگ عمومی فقط محصول published از فروشگاه active را می‌خواند.
7. ایجاد سفارش، سفارش خود فروشنده را رد می‌کند و موجودی، روش تحویل و تعداد را بررسی می‌کند.
8. پذیرش سفارش، کاهش موجودی و تغییر وضعیت سفارش را در D1 batch انجام می‌دهد.
9. نقش مدیر برای تأیید فروشگاه در مسیر جداگانه بررسی می‌شود.
10. مبالغ به‌صورت integer در واحد خرد ارز ذخیره می‌شوند؛ migration سفارش، عنوان و قیمت زمان سفارش را snapshot می‌کند.

## 3. ریسک‌ها و کارهای باقی‌مانده

### P1 — آزمون واقعی هم‌زمانی موجودی
در زمان ایجاد سفارش موجودی بررسی می‌شود، اما موجودی هنگام پذیرش فروشنده کم می‌شود. این الگو می‌تواند چند درخواست pending برای یک موجودی واحد ایجاد کند؛ پذیرش باید در شرایط رقابتی فقط برای سفارش‌هایی موفق شود که موجودی کافی دارند. تست هم‌زمانی با D1 محلی/آزمایشی لازم است و تست فعلی صرفاً mock است.

### P1 — اثبات صحت رفتار D1 batch
منطق پذیرش سفارش به نتیجه statementهای batch و تابع `changes()` وابسته است. تست mock فعلی جایگزین آزمون واقعی Cloudflare D1 نیست. باید در staging سناریوهای پذیرش هم‌زمان، موجودی ناکافی و شکست statement دوم اجرا شود.

### P2 — مدل سفارش چندقلمی
جدول `marketplace_order_items` ساختار چندقلمی دارد، اما endpoint فعلی فقط یک محصول در هر سفارش ثبت می‌کند. endpoint فهرست سفارش‌ها نیز با join اقلام ممکن است برای سفارش چندقلمی چند ردیف برگرداند. پیش از فعال‌سازی سبد خرید باید API و خروجی گروه‌بندی چندقلمی طراحی شود.

### P2 — اعتبارسنجی داده‌های فروشگاه
فیلدهای تماس و آدرس وب فروشگاه عمدتاً محدودیت طول دارند. پیش از نمایش عمومی باید سیاست اعتبارسنجی شماره تماس، URL، محتوای توصیف، گزارش محتوای نامناسب و محافظت در برابر لینک‌های فریبنده مشخص شود.

### P2 — کنترل چرخه عمر سفارش
قواعد فعلی وضعیت‌ها در endpoint اعمال می‌شوند، اما باید برای لغو پس از پذیرش، عدم پاسخ فروشنده، انقضای درخواست، اختلاف، بازپرداخت احتمالی در آینده و ثبت تاریخچه تغییر وضعیت، سیاست رسمی تعریف شود. پرداخت فعلاً به این سفارش‌ها متصل نیست.

### P2 — کنترل دسترسی و داده‌های مکانی
مختصات فروشگاه در داده عمومی استفاده می‌شود. رابط باید به فروشنده توضیح دهد که این مختصات مکان کسب‌وکار است و انتشار آن عمومی خواهد بود. مکان مشتری نباید بدون رضایت وارد جست‌وجو یا ذخیره‌سازی شود.

### P1 — تأیید وضعیت محیط واقعی
این بازبینی نمی‌تواند binding واقعی D1، اجرای migrationهای remote، Secrets، ایمیل، تنظیمات Cloudflare یا وضعیت Production را اثبات کند. این موارد باید جداگانه در داشبورد و staging تأیید شوند.

## 4. نتیجه

در کد، پایه قابل‌توجهی برای بازارگاه و درخواست سفارش وجود دارد؛ بنابراین ساخت مجدد آن توجیه ندارد. اقدام بعدی باید اجرای تست‌های واقعی D1، تکمیل کنترل چرخه سفارش و سپس ساخت لایه نیاز خریدار و تطبیق باشد.

هیچ تغییر اجرایی یا migration در این ممیزی اعمال نشده است. این سند صرفاً گزارش بازبینی ایستا است.
