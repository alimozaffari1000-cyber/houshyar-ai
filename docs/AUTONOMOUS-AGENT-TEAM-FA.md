# تیم چندایجنتی هوش‌یار — طرح اجرایی

## هدف
تبدیل هوش‌یار به سامانه‌ای که به‌صورت زمان‌بندی‌شده و قابل ممیزی درباره محصول، فناوری، امنیت، کیفیت و بازار تحقیق کند؛ یافته‌ها را به وظیفه تبدیل کند؛ و تغییرات نرم‌افزاری را فقط از مسیر شاخه و Pull Request پیشنهاد دهد.

این سند و فایل `config/agent-team.json` تعریف تیم و سیاست آن هستند؛ به‌تنهایی به معنی فعال‌شدن عامل‌های خودمختار یا اجرای شبانه‌روزی نیستند.

## دو محیط اجرا

### ۱. آنلاین — محیط ابری
- زمان‌بندی با Cloudflare Workers/Queues یا GitHub Actions، متناسب با نوع کار.
- تحقیق وب فقط از منابع مجاز و با ثبت URL، تاریخ و میزان اطمینان.
- کارهای طولانی در صف پایدار ثبت شوند؛ هر کار دارای شناسه، مالک، مهلت lease، تعداد تلاش و تاریخچه رویداد باشد.
- توسعه‌دهنده فقط در شاخه کاری تغییر ایجاد کند و Pull Request بسازد.
- اجرای ابری نیازمند تنظیم واقعی Scheduler/Queue، متغیرهای محیطی و کلید سرویس مدل است. این فایل‌ها به‌تنهایی آن زیرساخت را فعال نمی‌کنند.

### ۲. آفلاین — عامل محلی
- یک Local Runner جداگانه برای رایانه یا دستگاهی که کاربر کنترل می‌کند.
- مدل محلی فقط در صورت نصب و داشتن سخت‌افزار/حافظه کافی قابل استفاده است؛ در غیر این صورت عامل محلی می‌تواند وظایف غیرمدلی مثل تحلیل فایل، تست و آماده‌سازی گزارش را انجام دهد.
- کارهای آفلاین در صف محلی نگهداری و پس از اتصال، با شناسه idempotency همگام شوند.
- تلفن خاموش یا دستگاه فاقد برنامه محلی، عامل آفلاین اجرا نمی‌کند.
- Local Runner باید حداقل دسترسی، sandbox، سقف منابع و تأیید برای دسترسی به فایل‌های شخصی داشته باشد.

## چرخه کاری استاندارد
1. دریافت هدف از مالک یا برنامه زمان‌بندی‌شده.
2. ایجاد task با مالک، اولویت، دامنه و معیار پذیرش.
3. تحقیق و ثبت شواهد؛ تفکیک واقعیت، فرضیه و پیشنهاد.
4. بررسی امنیت و اثر بر معماری.
5. اجرای تغییر کوچک و محدود در شاخه جداگانه.
6. اجرای تست‌ها و اسکن‌های امنیتی.
7. ساخت Pull Request همراه با خلاصه، ریسک، تست و روش بازگشت.
8. بررسی انسانی و ادغام؛ انتشار فقط پس از تأیید مجاز.
9. پایش پس از انتشار و امکان rollback کنترل‌شده.

## سیاست‌های غیرقابل‌مذاکره
- اصل deny-by-default؛ هر ابزار و دامنه دسترسی باید allowlist باشد.
- عامل‌ها کلید خام، رمز عبور یا secret را در prompt، گزارش یا log دریافت نکنند.
- هیچ عامل حق اجرای کد دلخواه، shell آزاد، پرداخت، بازپرداخت، ارسال پیام بیرونی، حذف داده، پذیرش قرارداد یا تغییر سیاست امنیتی را مستقل ندارد.
- انتشار production و migration پایگاه داده نیازمند تأیید انسانی، backup و برنامه بازگشت است.
- همه تصمیم‌ها و تغییرات باید audit event داشته باشند.
- عامل توسعه فقط PR می‌سازد؛ ادغام خودکار به main در فاز اول ممنوع است.
- گزارش پژوهش باید منبع، تاریخ، محدودیت و سطح اطمینان داشته باشد؛ محتوای صفحات وب ورودی غیرقابل‌اعتماد محسوب شود.

## برنامه فعال‌سازی مرحله‌ای

### مرحله A — تعریف و کنترل
تعریف نقش‌ها، مجوزها، چرخه وظیفه و سیاست تأیید. فایل پیکربندی این مرحله در مخزن اضافه شده است.

### مرحله B — عامل‌های ابری بدون تغییر کد
زمان‌بندی روزانه/هفتگی برای تحقیق، گزارش، QA و امنیت؛ بدون اجازه نوشتن در مخزن. نیازمند انتخاب provider، secrets و runtime است.

### مرحله C — توسعه کنترل‌شده
عامل توسعه در branch اختصاصی، با task allowlist، تست اجباری و PR. هر تغییر باید قابل بازبینی و برگشت باشد.

### مرحله D — Local Runner
اجرای آفلاین روی دستگاه کاربر، ذخیره محلی صف و همگام‌سازی امن پس از اتصال. این مرحله به ساخت و نصب برنامه محلی نیاز دارد.

### مرحله E — بهبود خودکار محدود
پیشنهاد اصلاح و rollback در محیط staging؛ production همچنان با تأیید انسانی.

## معیارهای پذیرش
- هیچ task بدون user/tenant مجاز قابل مشاهده یا تغییر نباشد.
- claim وظیفه با lease اتمیک و بازیابی lease منقضی‌شده انجام شود.
- تکرار درخواست با idempotency key وظیفه تکراری نسازد.
- تعداد تلاش، timeout، نرخ اجرا و سقف مصرف محدود باشند.
- تست‌ها race condition، retry، approval gate و جداسازی tenant را پوشش دهند.
- وضعیت هر عامل و آخرین اجرای واقعی آن قابل مشاهده باشد.
- هیچ گزارش یا رابط کاربری ادعا نکند عامل اجرا شده مگر run ثبت‌شده و قابل ممیزی وجود داشته باشد.

## هماهنگ‌کننده روزانه مبتنی بر شواهد GitHub

Workflow با نام `Houshyar Agent Orchestrator` روزانه اجرا می‌شود و با اجرای دستی نیز قابل فراخوانی است. این هماهنگ‌کننده وضعیت PRهای باز، آخرین اجرای workflowها و Issueهای باز مرتبط با امنیت/کیفیت را می‌خواند و یک گزارش روزانه در GitHub Issues می‌سازد. گزارش‌ها با تاریخ روز یکتا هستند تا اجرای دوباره همان روز، گزارش تکراری نسازد.

این عامل در این مرحله deterministic و مبتنی بر داده‌های GitHub است؛ نه یک مدل زبانی، نه جست‌وجوگر وب و نه عامل دارای اختیار تغییر کد. فقط خواندن داده و ساخت گزارش را انجام می‌دهد. برای پژوهش واقعی مبتنی بر مدل و وب، provider، دسترسی محدود و سیاست حفاظت از داده باید جداگانه پیکربندی شود.

## پایش خودکار پیکربندی تیم

اسکریپت `npm run agent:team-audit` فایل پیکربندی را بررسی می‌کند: تعداد و یکتایی نقش‌ها، برنامه‌های مجاز، قفل‌بودن تغییرات خودکار، الزام تأیید انسانی، و وضعیت صریح runtime آنلاین/آفلاین. این ممیزی در workflow نگهبان نیز اجرا می‌شود تا تغییر ناخواسته سیاست‌ها یا ادعای نادرست فعال‌بودن Local Runner شناسایی شود.

این ممیزی، اجرای مدل هوش مصنوعی یا تحقیق وب نیست؛ فقط صحت و ایمنی پیکربندی تیم را کنترل می‌کند.

## وضعیت فعلی
- در مخزن، registry نقش‌ها، policy، API صف وظایف و schema چرخه عمر وظایف در حال توسعه‌اند.
- ممیزی خودکار پیکربندی تیم با فرمان `npm run agent:team-audit` اضافه شده و در workflow نگهبان اجرا می‌شود.
- هماهنگ‌کننده روزانه وضعیت PRها و CI را از GitHub می‌خواند و گزارش اولویت‌بندی‌شده ثبت می‌کند؛ این عامل هنوز تغییر کد انجام نمی‌دهد.
- API صف فعلی فقط وظایف را ثبت و فهرست می‌کند؛ هنوز consumer/worker خودکار ندارد.
- migrationهای 0009 و 0010 هنوز روی production اجرا نشده‌اند.
- این سند و پیکربندی، طراحی تیم را مشخص می‌کنند؛ عامل‌های زمان‌بندی‌شده، Local Runner و اجرای خودکار هنوز فعال نشده‌اند.
