# وضعیت امنیت حساب و احراز هویت

این سند وضعیت پیاده‌سازی در مخزن را توصیف می‌کند؛ وجود کد به معنی فعال‌بودن قابلیت در محیط واقعی نیست.

## دروازه فعال‌سازی

مسیرهای حساب فقط وقتی قابل استفاده‌اند که `AUTH_ENABLED=true` و binding پایگاه D1 با نام دقیق `DB` تنظیم شده باشد. برای ثبت‌نام، ارسال مجدد ایمیل و درخواست بازیابی رمز، تنظیمات سرویس ایمیل نیز لازم است.

پیش از فعال‌سازی در محیط عمومی:
1. migrationهای `0001`، `0002` و `0003` را ابتدا در D1 آزمایشی اجرا و بررسی کنید.
2. سرویس ایمیل HTTPS و متغیرهای سمت سرور `EMAIL_API_URL`، `EMAIL_API_KEY`، `EMAIL_FROM` و `APP_BASE_URL` را آماده کنید.
3. ثبت‌نام، تأیید ایمیل، ورود، خروج، ارسال مجدد ایمیل و بازیابی رمز را در staging به‌صورت end-to-end آزمایش کنید.
4. فقط پس از عبور از گیت‌های انتشار، `AUTH_ENABLED=true` را فعال کنید.

## محدودیت درخواست و کنترل نرخ

- بدنه JSON مسیرهای احراز هویت حداکثر ۸ KiB است؛ نوع محتوا و ساختار JSON نیز اعتبارسنجی می‌شود.
- کنترل نرخ از پنجره ثابت ۱۵ دقیقه‌ای استفاده می‌کند.
- کلیدهای محدودسازی از هش SHA-256 ایمیل نرمال‌شده و IP دریافت‌شده از هدر Cloudflare ساخته می‌شوند؛ ایمیل و IP خام در کلیدهای جدول ذخیره نمی‌شوند.
- سقف‌های پیش‌فرض در هر پنجره ۱۵ دقیقه‌ای: ثبت‌نام ۵، ورود ۱۰، تأیید ایمیل ۱۰، ارسال مجدد تأیید ۳، درخواست بازیابی رمز ۳ و ثبت رمز جدید ۵ تلاش است.
- مقادیر قابل تنظیم از سقف ۳۰ تلاش بیشتر نمی‌شوند.
- در صورت نبود D1، پاسخ نامعتبر از D1 یا خطای ذخیره‌سازی، مسیرهای دارای کنترل نرخ با پاسخ 503 متوقف می‌شوند (fail-closed).
- مسیرهای تغییردهنده حساب، وجود هدر `Origin` هم‌مبدأ را الزامی می‌کنند؛ درخواست فاقد Origin یا با مبدأ دیگر رد می‌شود.

## ثبت‌نام و تأیید ایمیل

- ثبت‌نام رمز عبور ۱۲ تا ۱۲۸ نویسه‌ای می‌پذیرد و حساب را در وضعیت `pending` ایجاد می‌کند.
- توکن تأیید تصادفی و یک‌بارمصرف است و ۲۴ ساعت اعتبار دارد.
- فقط هش SHA-256 توکن در D1 ذخیره می‌شود؛ مقدار خام توکن در لینک ایمیل ارسال می‌شود.
- تأیید، فعال‌سازی حساب و مصرف توکن را در یک batch انجام می‌دهد.
- پاسخ عمومی ثبت‌نام و ارسال مجدد طوری طراحی شده که وجود یا عدم وجود ایمیل ثبت‌شده را آشکار نکند.

## بازیابی رمز عبور

- درخواست بازیابی برای حساب فعال، توکن تصادفی یک‌بارمصرف با اعتبار ۳۰ دقیقه ایجاد می‌کند.
- فقط هش توکن در D1 نگهداری می‌شود.
- رمز جدید باید ۱۲ تا ۱۲۸ نویسه داشته باشد.
- تغییر رمز، مصرف توکن و ابطال نشست‌های قبلی را در یک batch انجام می‌دهد.
- پاسخ عمومی درخواست بازیابی، وجود یا عدم وجود حساب را افشا نمی‌کند.

## نشست و نگهداری رمز

- رمز عبور با PBKDF2-HMAC-SHA-256 و ۳۱۰٬۰۰۰ تکرار مشتق می‌شود؛ salt تصادفی مستقل برای هر حساب ذخیره می‌شود.
- کوکی نشست دارای ویژگی‌های `HttpOnly`، `Secure` و `SameSite=Lax` است و حداکثر عمر آن ۳۰ روز است.
- توکن خام نشست در D1 ذخیره نمی‌شود؛ هش آن نگهداری می‌شود.
- تغییر رمز، نشست‌های قبلی کاربر را باطل می‌کند.

## پاک‌سازی دوره‌ای D1

Workflow با نام `Houshyar D1 Security Cleanup` در `.github/workflows/d1-security-cleanup.yml` تعریف شده است و رکوردهای منقضی/مصرف‌شده توکن‌ها، نشست‌های منقضی/باطل و پنجره‌های منقضی محدودیت نرخ را پاک می‌کند.

این workflow فقط در صورت وجود هر سه GitHub secret زیر به مقصد مشخص‌شده وصل می‌شود؛ اگر هرکدام تنظیم نشده باشد، پاک‌سازی را رد می‌کند:
- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`
- `CLOUDFLARE_D1_DATABASE_NAME`

وجود workflow به‌تنهایی اثبات نمی‌کند که secrets تنظیم شده‌اند یا پاک‌سازی واقعی اجرا شده است. وضعیت اجرای آن باید در GitHub Actions بررسی شود.

## وضعیت production و محدودیت‌های بررسی

- کد پایه ثبت‌نام، ورود، نشست، تأیید ایمیل، بازیابی رمز و محدودیت نرخ در شاخه اصلی وجود دارد.
- فعال‌بودن D1، migrationها، سرویس ایمیل و secrets در Cloudflare از روی کد مخزن قابل اثبات نیست.
- تا تکمیل گیت‌های انتشار و آزمون end-to-end، احراز هویت و سهمیه را در production فعال نکنید.
- این کنترل‌ها جایگزین تست نفوذ مستقل، بازبینی امنیتی عملیاتی یا بازبینی حقوقی حریم خصوصی نیستند.
