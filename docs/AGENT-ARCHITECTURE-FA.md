# معماری تیم ایجنت‌های هوش‌یار
نسخه پیشنهادی: ۱.۰
وضعیت: طراحی فنی؛ هنوز به معنی فعال بودن عامل‌های مستقل در محیط عملیاتی نیست.

## ساختار تیم

### 1) Orchestrator — مدیر جریان کار
- دریافت هدف، تشخیص نوع درخواست و ساخت برنامه مرحله‌ای.
- انتخاب فقط عامل‌ها و ابزارهای مجاز برای همان وظیفه.
- جمع‌آوری خروجی‌ها، حل تعارض و ارائه نتیجه نهایی.
- محدودیت: خودش مجوز دسترسی گسترده یا اجرای اقدام بیرونی ندارد.

### 2) Research Agent — پژوهشگر
- جست‌وجوی چندمنبعی، استخراج نکته‌ها، تاریخ‌گذاری و ارجاع.
- تشخیص تناقض و جدا کردن واقعیت از تحلیل.
- خروجی ساختاریافته: پرسش، یافته، منبع، تاریخ، اطمینان، شکاف اطلاعات.
- دفاع: متن صفحات وب داده غیرقابل اعتماد است و هرگز دستور سیستم را تغییر نمی‌دهد.

### 3) Builder Agent — سازنده/برنامه‌نویس
- طراحی و تولید کد، اسناد، جداول و نمونه‌های اولیه.
- کار در محیط محدود و شاخه جدا؛ ارائه diff و تست.
- محدودیت: عدم دسترسی به secretها و عدم انتشار مستقیم به production.

### 4) Analyst Agent — تحلیلگر
- تحلیل داده، مقایسه گزینه‌ها، محاسبات و سناریوها.
- نمایش فرض‌ها، فرمول‌ها، دامنه خطا و منبع داده.
- در موضوع مالی/پزشکی/حقوقی، هشدار ریسک و عدم ارائه قطعیت بی‌پشتوانه.

### 5) Content & Language Agent — نویسنده و مترجم
- تولید، ویرایش و بومی‌سازی متن.
- حفظ اصطلاحات تخصصی و تطبیق لحن با مخاطب.
- بازبینی ترجمه چندزبانه و نشانه‌گذاری محتوای تولیدی.

### 6) QA & Accessibility Agent — آزمون‌گر
- اجرای تست واحد، یکپارچه، smoke، build، مرورگر و موبایل.
- بررسی RTL، صفحه‌کلید، کنتراست، برچسب‌های دسترس‌پذیری و خطاهای UI.
- خروجی: شدت، مراحل بازتولید، انتظار/واقعیت و شواهد.

### 7) Security Guardian — نگهبان امنیت
- بررسی dependency، secret leakage، مجوز workflow، ورودی‌ها، rate limits و خطاهای پیکربندی.
- تولید هشدار و پیشنهاد patch؛ تغییر خودکار فقط در شاخه آزمایشی و پس از تست.
- محدودیت: عدم دسترسی به کلیدها، عدم تغییر حساب Cloudflare، عدم حذف داده و عدم ادغام/انتشار خودکار.
- هیچ عامل دیگری نمی‌تواند بررسی امنیتی خودش را تأیید نهایی کند.

### 8) Product & Growth Agent — مدیر محصول و رشد
- تحلیل بازخورد، قیف فعال‌سازی، نرخ بازگشت و هزینه هر کاربر.
- پیشنهاد آزمایش‌های محصولی و قیمت‌گذاری؛ اجرای آزمایش فقط با مجوز.
- عدم استفاده از داده شخصی برای تبلیغات بدون رضایت روشن.

## قرارداد اجرای هر عامل
هر عامل باید این داده‌ها را دریافت/تحویل دهد:
- task_id، هدف محدود، ورودی‌های مجاز، ابزارهای مجاز، سقف زمان و بودجه.
- plan، خروجی، منابع، تست‌ها، هشدارها، میزان اطمینان و وضعیت.
- وضعیت‌های مجاز: queued، running، needs_approval، completed، failed، cancelled.

## سیاست اختیار و ایمنی
1. مجوزها پیش‌فرض deny و به‌ازای هر ابزار تعریف می‌شوند.
2. دسترسی به داده فقط در حد همان کاربر و همان پروژه.
3. فایل و متن وب، prompt injection بالقوه محسوب می‌شوند؛ دستورهای داخل آنها اجرا نمی‌شوند.
4. عملیات برگشت‌ناپذیر، بیرونی یا مالی نیازمند تأیید صریح کاربر است.
5. عامل‌ها نمی‌توانند secret را بخوانند، چاپ کنند یا در log ذخیره کنند.
6. محدودیت token، زمان، تعداد فراخوانی ابزار و هزینه برای هر وظیفه اعمال می‌شود.
7. تمام اقدام‌های ابزار با شناسه عامل، task_id، زمان و نتیجه ثبت می‌شود؛ متن محرمانه گفتگو در log ثبت نمی‌شود.
8. QA و Security باید مستقل از عامل سازنده نتیجه را بررسی کنند.
9. انتشار production فقط از مسیر CI/CD با کنترل انسانی و بررسی موفق همه gateها.
10. اگر مدل/ابزار در دسترس نبود، سیستم باید خطای شفاف بدهد و ادعای انجام کار نکند.

## ترتیب پیاده‌سازی
- مرحله A: registry و schema عامل‌ها، بدون اجرای خودمختار.
- مرحله B: اجرای امن Research/Analyst/Content با ابزارهای read-only.
- مرحله C: Builder در sandbox و تولید artifact قابل دانلود.
- مرحله D: QA و Security در CI با گزارش خودکار.
- مرحله E: Orchestration چندعاملی، صف کار و امکان لغو.
- مرحله F: Product/Growth با داده‌های تجمیعی و رضایت‌محور.

## معیار پذیرش
- هر عامل تست قرارداد و تست مجوز داشته باشد.
- تست prompt injection روی فایل و صفحات وب.
- تست جداسازی tenant و جلوگیری از دسترسی بین کاربران.
- سقف مصرف و timeout در تمام مسیرهای مدل/ابزار.
- مسیر لغو کار و پاک‌سازی داده موقت.
- گزارش شفاف اینکه چه چیزی واقعاً اجرا شده و چه چیزی فقط پیشنهاد شده است.


## هماهنگ‌کننده محدود چندایجنتی

- ماژول `functions/api/_lib/agent-coordinator.js` برای درخواست‌هایی که حداقل دو سیگنال تخصصی دارند، حداکثر دو متخصص را با ترتیب قطعی انتخاب می‌کند.
- هر متخصص فقط یک فراخوانی مدل با سقف خروجی محدود دریافت می‌کند؛ سپس یک فراخوانی سوم پاسخ‌ها را یکپارچه می‌کند. سقف کل: سه فراخوانی مدل برای هر درخواست هماهنگ‌شده.
- شکست یک متخصص مانع استفاده از خروجی متخصص موفق نمی‌شود؛ اگر جمع‌بندی شکست بخورد، خروجی‌های محدود متخصصان برگردانده می‌شود.
- مسیر API فقط با `body.mode = "coordinated"` و تنظیم سروری `AGENT_COORDINATION_ENABLED=true` قابل استفاده است. پیش‌فرض خاموش است.
- این نسخه برنامه‌ریز deterministic است، نه عامل خودمختار: هیچ ابزار خارجی، شبکه، فایل، پرداخت، انتشار یا تغییر داده‌ای به متخصصان واگذار نمی‌شود.
- برای جلوگیری از افزایش ناخواسته هزینه، درخواست‌های عادی همان مسیر تک‌فراخوانی قبلی را حفظ می‌کنند. پیش از فعال‌سازی محیطی، هزینه و timeout باید در staging اندازه‌گیری شوند.
- تست‌ها رفتار طرح، سقف مراحل، ترتیب اجرا، خطای جزئی، شکست کامل و شکست جمع‌بندی را پوشش می‌دهند.
